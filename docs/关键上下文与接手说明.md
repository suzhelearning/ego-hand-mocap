## 项目目的

使用 OptiTrack 动捕为 Ego 手部识别提供 Ground Truth，比较两侧21点三维位姿。保存原始视频、动捕与派生结果，支持以后更换或优化 Ego 图像算法，不仅服务一次评测。

## 用户已明确的信息

- 两侧数据均离线处理；比较前需要时间戳对齐，不要求实时系统。
- 手部 marker 贴在手背某些关节附近，用 MANO 拟合生成类似 MediaPipe 格式的21个三维点，位于动捕世界系，作为参考 Ground Truth。
- Ego 侧也估计类似 MediaPipe 的21点三维位姿，手与头戴之间有位姿关系。
- Ego 每段录制都会重新设置自己的坐标系；采集中头戴实际在动捕世界系下移动。
- 因此必须保存逐帧头戴 marker 刚体位姿。初始默认位姿不能代替整段动态轨迹。
- 相机光学系相对 marker 刚体系的位置和朝向需要通过标定求出；人工布置和采集后可计算求解，不是必须用尺子测光心。
- 原对话中用户提到 OptiTrack 为普通版本、没有 Trained Markerset，并担心手部 marker 遮挡后重新出现时 ID 改变。这是需求背景；具体可用功能、版本和导出接口尚未核实。

## 坐标系及变换方向

统一 T_AB 表示从B系到A系，齐次列向量左乘。

- W：OptiTrack世界系。
- B：头戴设备marker刚体系。
- C：Ego算法实际输出所用相机/头戴参考系，是否等于cam0_optical尚待确认。
- E：Ego本段录制初始化的世界系，每段可能不同。
- T_WB(t)：动捕测得的头戴刚体动态位姿。
- T_BC：待标定的固定外参，安装与刚体定义不变时可复用。

若Ego21点在当前C系：

```text
p_W_Ego(t) = T_WB(t) * T_BC * p_C_Ego(t)
p_C_GT(t) = inverse(T_BC) * inverse(T_WB(t)) * p_W_GT(t)
```

若Ego21点在E系：

```text
p_W_Ego(t) = T_WE * p_E_Ego(t)
T_WE = T_WB(t) * T_BC * inverse(T_EC(t))
```

T_WE应按每段录制确定。若Ego发生漂移或重定位，固定T_WE不能消除时变误差。分别使用Ego世界轨迹或动捕头戴轨迹，评估中包含的定位误差不同，应明确报告。

若输出“手局部点＋手相对头戴位姿”，先得到C系点；若已是C系点，不能重复施加手位姿。

重新贴marker、改变Motive刚体pivot/局部轴或机械安装松动后，应重新核验T_BC。

## 样例数据已经确认的事实

样例现保存为 `ego_data/head_000205/head_000205.h5` 及同目录的四路 MP4；已校验一致后删除重复 ZIP 和 H5 副本。完整参数见 `calibration/head_000205_calibration_full.json`。

- 标定内容在H5 `/calib/calibration_full.json`，为JSON字符串。
- `rig.body_frame=cam0_optical`，物理ID为m00_b_imx334，即左RGB；不是OptiTrack刚体系或世界系。
- cam0=RGB_left，cam1=RGB_right，cam2=IR_left，cam3=IR_right。
- 实际RGB 2500×2160、30Hz、每路257帧；IR 1280×800、50Hz、每路428帧。旧标定的IR rate_hz=30，不应覆盖实际录制频率。
- `canonical_camera_transforms.transforms.camN` 明确 cam0_optical→camN_optical。T_i0方向满足p_i=T_i0*p_0；求其他相机世界位姿时使用inverse(T_i0)。
- `transform_convention`：row_major，homogeneous_column，平移m，角度rad；reshape(4,4)无需转置。存储顺序不等于行向量约定。
- 旧`cameras.*.T_BS`与canonical矩阵一致，历史语义为reference/body→sensor，不能凭字段名猜方向。
- 相机中心在cam0系中是-R^T*t，不是外参平移列本身。
- 未发现OptiTrack世界系或marker刚体系到相机的外参。
- 未发现相机光学系逐轴方向的显式声明；IMU的FLU约定不能直接套给相机。

### 会影响后续正确性的风险

1. 四相机都同时有`distortion_coefficients`和`distortion_coefficients_full`；RGB两套鱼眼类系数不同，IR还涉及rational与opencv-fisheye两种模型。没有证据确定哪套被实际消费；不能默认_full优先或混用模型。
2. 视频配置：cam0旋转180°；cam1不旋转；cam2镜像；cam3旋转180°且镜像。虽然标定绑定写compatible，仍未确认内参对应处理前还是处理后图像，以及组合处理顺序。不能盲目再翻转。
3. `quality.requires_recalibration=true`；相机—IMU时间偏移未标定，IMU六面质量检查失败后曾强制启用。相机独立验证`not_run`。
4. provenance仍记录旧JSON/YAML外参冲突；当前字段一致不等于已独立验证真实精度。

## 时间同步的当前方案与限制

详细流程见 `时间同步方案.md`。建议每次录制开头和结尾各加入不规律头部转动，利用IMU角速度模长与动捕头戴旋转速度先做互相关和偏移细化，再检查多窗口漂移。

采用带时间原点的仿射映射：

```text
t_mocap = t_mocap0 + a * (t_ego - t_ego0) + b
```

- 相机逐帧使用`timestamp_ns`；`pts_ns`是视频相对时间。
- 同设备`CLOCK_MONOTONIC`只保证设备内计时基准，不与动捕主机自动共享零点。
- H5的`camera_imu_offset_ns=null`，故IMU同步不能证明图像曝光同步。还需核实相机时间戳语义，并用独立可见运动目标验证图像时刻。
- 动捕使用采集时间而非网络接收时间，NatNet字段能力需结合实际版本确认。
- 最新用户决定：以本 PC 时钟为统一基准，离线为每帧 RGB 匹配时间最近的动捕帧，保存原始时间戳、映射时间及配对时间差，不插值；无效跟踪和缺口需显式标记。
- 当前动捕数据在 Windows `~/Desktop/syz/ego-hand/`。NatNet 保存的 H5 只有刚体数据，手部 marker 具体数据来自 Motive 导出的 C3D（用户说明，目录及文件尚未检查）。须分别核实刚体 H5 时间戳来源及 C3D 到同次录制时间轴的帧对应关系，不能将 NatNet 字段定义直接视作 H5 已保存字段。
- 不使用待测手部算法的误差最小化来决定同步量，避免影响评估独立性。
- 当前没有实际求出的a、b、同步残差或达标精度；搜索步长小不代表真实精度高。

## Ego 设备现场上下文（2026-10-28）

以下来自对设备及本机的现场只读检查和临时 USB 模式对照试验；是当时固件和连接状态的快照，不代表所有采集会话都相同。设备运行 Buildroot/Rockchip RK3576。接入地址为 USB RNDIS `192.168.100.1`，另有设备热点 `wlan0-bootstrap-0317`、热点侧地址 `192.168.4.1`；凭据不写入项目文档。曾观察到设备系统日期落后于本机，跨设备对时前应检查 `/run/rk3576-time-sync` 的可信时间状态，不要直接按日志墙上时间对齐。

### 左 RGB 时间戳现场核实（2026-10-28）

当前固件 capture 直接采用 V4L2 buffer 的 CLOCK_MONOTONIC 时间戳。虽然 flags 声明 source=EOF，但 Rockchip 6.1 的 CIF→ISP readback 代码链实际把 CIF CSI frame-start 中断取得的 `fs_timestamp` 传到 mainpath buffer；当前设备的同族驱动符号和 32 ms 读出 + 9 ms ISP ≈ 42 ms delay 也支持这一点。因此该值更可能是 CIF FS/SOF 软件时间戳，不能据此认定曝光开始/中点；物理相位和中断延迟仍未确认。249 帧实测 DQBUF 事件比 buffer 时间戳晚 42.803–56.643 ms（中位数 44.136 ms），这是完整读出与下游交付延迟，不是曝光修正量。详见 `Ego左RGB时间戳核实_20261028.md`。当前固件结论不能直接追认历史 H5。

左路可订阅 `FRAME_SYNC` 的节点是 `/dev/v4l-subdev5`（`rkcif-mipi-lvds1`），不是 `/dev/v4l-subdev4`（`rkisp-isp-subdev`）。持续采集时等待 8 秒未收到事件；同版本 Rockchip 6.1 源码显示当前 MIPI 路径通过内部 `RKISP_VICAP_CMD_SOF` 传递 SOF，不向该 CIF 子设备的用户态队列发送 `FRAME_SYNC`。因此不能靠该事件取得物理 SOF/SOE。

从物理图像参考时刻到 H5 `timestamp_ns` 可分为曝光/逐行读出几何、传感器到 CIF 硬件传输、CIF 中断与软件读时钟。前两段中的曝光和滚动快门差是数十毫秒量级的主要项；硬件传输和软件中断通常为纳秒到微秒，在粗对齐中可忽略。H5 保存的是 CIF FS 事件时间，不是数据完成读出、DQBUF 或写盘时间；后续约 44 ms 中位 DQBUF 延迟不能拿来修正曝光。跨设备仍需独立求 Ego 单调时钟到 Ubuntu/OptiTrack 时钟的仿射映射。

### 录制服务与触发

- `/etc/init.d/S11quad_cam_streamer` 启动 `/usr/bin/quad_cam_streamer /etc/quad_cam_streamer/config.json`；这是相机、IMU 和录制的核心进程。二进制保留 `EurocRecorder::start_recording()`、`stop_recording()`、`toggle_recording()`、`ParamController::handle_command()` 等符号及 `euroc_recorder.cpp`、`param_controller.cpp` 文件名，但现场未取得对应 C++ 源码正文。
- 当前录制配置启用实体按键：`input_name=record-connect-key`、`record_key_code=149`（KEY_PROG2）。长按还有 Wi-Fi 重配对用途；不能假定每次按下都开始录制，校准、采集配置、设备就绪及关机抑制等条件可能拒绝开始。语音配置也启用“开始录制”“停止录制”。
- Web 界面的 `recordToggle()` 发送 `{"record_toggle":true}`，**切换**而非单独开始；设备 `/usr/share/web_viewer/gateway/gateway.py` 的 `/ws/control` 将 JSON 经 ZeroMQ REQ/REP 代理到 `tcp://127.0.0.1:5570`。只读 `{"query":true}` 曾返回 `{"recording":{"active":false},"status":"ok"}`，没有做真实按键/录制试验。
- `/etc/init.d/S98ego-collection` 启动 `uvicorn app.server:app`，负责数据上传代理，不是实体录制键或相机录制核心。设备录制文件根路径配置为 `/mnt/sdcard/SD`。

### 按键事件与跨设备时间

- 录制程序在 `0.0.0.0:5565` 提供 ZeroMQ PUB 按键/录制状态事件。设备 Web 网关订阅该端口，按 13 字节小端数据解析：`timestamp u64`、`is_recording u8`、`seq u32`，再通过 `/ws/telemetry` 向浏览器提供 `{"type":"key","ts":...,"is_recording":...,"seq":...}`。这是带设备时间戳的**状态事件**，不等同于实体键电平或经验证的硬件同步脉冲；其他机器需主动订阅，不能用网络到达时间代替采样时刻。
- 当前配置启用 `wifi_bridge`，录制二进制中可见 `recording.set`、`effective_timestamp_ns`、`RECORD_ACK` 和 `effective_rk_ns` 等跨设备定时/确认协议痕迹；桥接服务监听本机 `127.0.0.1:42110/42111`，协议状态显示左右手设备各自的同步质量和确认计数。**检查时** `/run/wlan0-bootstrap/device-bridge-status.json` 显示 `binding_configured=false`、左右设备均 `absent`、`sync_ok=0`、`tx=0`，Wi-Fi 后端报告 `wlan0` 不存在；不能声称按键已经向别的设备完成同步发送或被接收。
- 按键事件的原始设备时间戳与 OptiTrack 主机没有自动共享时间原点。即使将其当作候选事件标记，也不能替代本文件既定的离线仿射时间映射和图像曝光时刻验证；未实测端到端事件延迟或跨设备同步精度。

### USB 断线证据与临时绕过

- USB ID `2207:0012`（Rockchip），设备提供 RNDIS、ACM 和 ADB 复合功能。故障时本机 USB 3 端口 `2-9` 约每 1.2 秒发生整台 USB 设备的 `USB disconnect`，先于网卡被 `rndis_host` 注销；枚举出现 `-71` 协议错误、`-110` 超时。Ego 自身运行时间持续增长，`dwc3` 记录反复 `device reset`；因此不是 NetworkManager、DHCP 或单独 RNDIS 网卡驱动导致的 IP 层掉线，ADB 无效也属同一 USB 故障。USB 3 的线材、接头、主机端口及设备侧 PHY/固件尚未分别排除，**未认定具体硬件根因**。
- 对照试验：临时锁住 `/var/run/.usbdevice.lock` 阻断 gadget 更新约 15 秒，设备侧仍发生 25 次 `dwc3 device reset`；临时暂停设备 `adbd` 约 15 秒，本机仍有 12 次 USB 断线。两种软件动作都不是已证明的根因。
- 将 gadget 的运行时 `max_speed` 改为 `high-speed`（USB 2.0）后，本机枚举为 480M，20/20 和随后 60/60 次 ping 成功，USB SSH、ADB shell 成功；自动恢复 USB 3 后断线复现。用户选择**临时 USB 2.0 绕过**：再次设置后 30 秒无 USB 断线记录；降低理论链路上限至 480 Mbps，尚未测四路预览/数据导出吞吐。未修改开机配置，重启后需重做；这不是 USB 3 根因修复。

临时重做时，通过独立网络登录 Ego（避免 USB SSH 在模式切换中断开），在设备上运行以下**仅运行时**切换命令；BusyBox `flock` 不支持 `-w`。操作会瞬时重新枚举 USB，失败时 `EXIT` trap 尝试恢复旧速率：

```sh
flock /var/run/.usbdevice.lock sh -c '
set -e
G=/sys/kernel/config/usb_gadget/rockchip
old=$(cat "$G/max_speed")
udc=$(cat "$G/UDC")
test -n "$udc"
restore() {
    echo "" > "$G/UDC"
    echo "$old" > "$G/max_speed"
    echo "$udc" > "$G/UDC"
}
trap restore EXIT
echo "" > "$G/UDC"
echo high-speed > "$G/max_speed"
echo "$udc" > "$G/UDC"
trap - EXIT
cat "$G/max_speed"
'
```

输出 `high-speed` 后，在本机检查 USB 枚举速率、`ping 192.168.100.1`、ADB shell 和内核断线日志。需要恢复 USB 3 时按相同锁定/解绑/重绑顺序设回原值 `super-speed-plus`，但原故障会重现。**根因隔离仍应优先更换 USB 数据线、电脑接口，并用 USB 2/3 对照测试区分链路与固件。**

## MANO参考结果的边界

marker是皮肤表面观测，不等于骨骼关节中心；需明确marker到MANO表面的对应及偏移。21点参考结果是模型拟合结果，包含marker误差、软组织运动和模型/拟合误差。

稀疏手背marker可能不足以约束全部手指自由度。必须保留原始轨迹、身份/遮挡/补点标记、拟合残差和有效性，不能仅保存21点或把不可观测自由度当成准确真值。

beta求解方式未确定；同一人的beta跨帧共享是建议而非已实施方案。MANO模型版本、左右手、单位、pose定义、指尖补充与21点导出规则均需固定。与MediaPipe逐点核对解剖定义，尤其腕点和拇指。
