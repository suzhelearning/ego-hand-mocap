# Ego 左 RGB 时间戳现场核实

检查日期：2026-10-28（Asia/Shanghai）。通过 ADB 连接当前 Ego，未重启采集、未切换录制、未改曝光配置。临时 trace 实例已删除。

## 结论

**高置信度确认：当前采集路径使用 V4L2 buffer 时间戳，而且该值很可能不是帧结束时间，而是 CIF 帧起始中断处的 `fs_timestamp`。** `flags=0x00002001` 中的 source 位为零，只代表驱动采用了 V4L2 的默认 `TSTAMP_SRC_EOF` 编码，不能据此证明时间戳是在 EOF 打的。Rockchip 6.1 的 CIF→ISP 代码链会把这个起始时间传入 raw buffer，再传到 offline ISP 的输出 buffer；当前设备内核符号入口与该实现一致。逐帧物理曝光相位及 CIF 中断相对传感器波形的延迟仍未确认，不能把下面的取帧延迟当作曝光修正常数。该结论只覆盖当前设备固件，不足以追认历史 head_000205.h5 的生成固件。

- 左 RGB：m00_b_imx334 4-001a，/dev/video44，rkisp_mainpath，2500×2160，30 Hz。
- 设备启动日志：`[V4L2] Timestamp contract on /dev/video44: flags=0x00002001 domain=CLOCK_MONOTONIC source=EOF`。
- 二进制 `V4L2Camera::capture(unsigned long&, unsigned long&, unsigned int&, int)` 在 0x101998 调用 VIDIOC_DQBUF（ioctl request 0xc0585611）；0x101c08–0x101c24 从 v4l2_buffer.timestamp 的 timeval 取秒及微秒，计算 `tv_sec*1000000000 + tv_usec*1000`，写出第二个引用参数。没有用取帧完成时的 clock_gettime 覆盖该值。另一个引用参数为图像字节数。
- `CapturedVideoTimestampSource::next_timestamp_ns(int, unsigned long)` 在 0xecd90–0xecd94 直接返回传入时间（mov x0,x2; ret）。进程环境未发现 QCS_TEST 时间戳注入变量。但本次未实际新录制并核对 H5 写入链路。
- 设备内核为 RK3576 Linux 6.1.99，`/proc/kallsyms` 中存在与 Rockchip 6.1 实现对得上的 `rkcif_deal_sof`、`rkcif_s_rx_buffer`、`rkcif_buf_done_prepare`、`rkisp_dmarx_get_frame` 等入口。
- Rockchip 6.1 的 `rkcif_deal_sof()` 在 CSI frame-start 中断中执行 `stream->readout.fs_timestamp = rkcif_time_get_ns()`；frame-end 的中断路径仍把 `fs_timestamp` 写入 V4L2 buffer timestamp。offline ISP 的 readback 路径将该值作为 `frame_timestamp` 传入 ISP，最终赋给 `/dev/video44` 的 buffer。
- 因此，`source=EOF` 与实现冲突或至少没有描述实际来源。`timestamp_ns` 的事件语义更接近 **CIF 收到的帧起始（FS/SOF）**，不是传感器曝光开始、曝光中点、帧结束或 DQBUF。CIF 中断本身距传感器物理 SOF 的延迟仍没有硬件波形证据。

### 当前左 RGB 参数

| 项目 | 当前值 |
|---|---|
| 传感器 | Sony `m00_b_imx334 4-001a` |
| 传感器格式 | `SRGGB10_1X10`，3864×2180，30 fps |
| MIPI | CSI-2 D-PHY，4 lanes |
| sensor link frequency | 445.5 MHz |
| sensor pixel rate | 356.4 MHz |
| CIF crop | offset `(680, 8)`，2500×2160 |
| V4L2 输出 | `/dev/video44`，`rkisp_mainpath`，NV12，2500×2160 |
| 输出 stride / size | 2512 B / 8,138,880 B |
| 时钟 | sensor XVCLK 24 MHz；ISP core 702 MHz；CIF/ISP AXI 594 MHz；AHB 198 MHz |
| VTS | 2180 active + 70 vblank = 2250 lines |
| CIF readout / rate | 32 ms / 33 ms |
| ISP 处理时间 | 约 9 ms |
| ISP offline 输出状态 | 左 RGB snapshot 为 `frame1`、`delay: 42 ms` |

当前驱动 exposure 控制值为 2228（范围 5–2246），vertical blanking 为 70，analogue gain 原始控制值为 80（范围 0–240）。按 `2250 lines @ 30 fps` 可得行周期约 14.815 µs；2160 个有效输出行约为 32.00 ms，与 CIF 的 `readout=32 ms` 吻合。若 exposure 控制当前确实按整行生效，2228 行约为 33.0 ms。应用配置中的 `exposure_us=2000` 是请求值；由于 `auto_exposure=true`，不能把它当作当前实曝光值。gain=80 也只是驱动/寄存器控制码，不能直接写成倍数。

同版本 Rockchip IMX334 驱动确认 `V4L2_CID_EXPOSURE` 以整行计数，并写入 `SHR0 = VTS - exposure`，所以上述 2228 行控制值可按行周期换算为约 33.0 ms。自动曝光控制器仍可在光照变化时修改该值，因此这个时长不属于固定曝光配置。

### 短时稳定性复核

2026-10-28 对持续工作的左 RGB 做只读采样：约 12 秒内连续读取 60 次 `exposure / vertical_blanking / analogue_gain`，全部保持 `2228 / 70 / 80`；随后以 `/proc/rkcif-mipi-lvds1` 的 frame counter 测量 `10.020 s`，新增 301 帧，折合 `30.0399 fps`。CIF 当时报告 `readout=32 ms`、`rate=33 ms`、`fps=30`，ISP 报告处理约 `9 ms`、输出状态延迟 `42 ms`。

这支持短时帧节拍稳定、当前曝光值未漂移，但不能证明整段录制恒定。`auto_exposure=true`，环境变化会改变曝光；设备日志显示左 RGB 启动为 `sync_mode=0 (sw sync)`，CIF 报告 `Sync Mode:no sync`，所以也不能把本地稳定的 30 Hz 节拍误认为与 Ubuntu/OptiTrack 或另一相机具有固定硬件相位。

Linux API 对 EOF 的定义为帧最后像素接收/发送时刻，对 SOE 的定义为曝光开始，见 [Linux V4L2 Buffer Flags](https://www.kernel.org/doc/html/v5.5/media/uapi/v4l/buffer.html)。不能把 EOF 直接解释为曝光结束。

## 实测 timestamp→DQBUF 延迟

用独立 ftrace instance，trace_clock=mono，仅启用 `v4l2:v4l2_dqbuf` 并过滤 minor=44。有效样本 249 帧，sequence 90721–90969，跨度约 8.27 秒，无序号缺口。计算 trace 中 DQBUF 事件时刻减去同一事件的 buffer timestamp（同设备 monotonic 域）；不是 PC 收包时间，也不是函数返回/图像变换结束时间。由于 timestamp 很可能是 CIF 帧起始时刻，这个差值包含完整帧读出、ISP 和排队，而不是“EOF→DQBUF”。

| 指标 | DQBUF事件减buffer时间戳 |
|---|---:|
| 最小 | 42.803 ms |
| 中位数 | 44.136 ms |
| 平均 | 45.678 ms |
| P95（排序下取整） | 55.726 ms |
| 最大 | 56.643 ms |
| 标准差（总体） | 3.844 ms |

帧时间戳间隔中位数 33.3335 ms，范围 32.755–33.892 ms，标准差 0.174 ms。**帧周期较稳定，但取帧延迟不是固定值**；以上仅是短时间窗口，不能证明长期或不同负载下稳定。

## 曝光仍需确认的原因与下一步

现场 `/proc/rkcif-mipi-lvds1` 报告 readout=32 ms；`/proc/rkisp-vir0` 报告 offline ISP 路径（一次快照输出 delay=42 ms）。约 32 ms 读出加约 9 ms ISP 处理，与约 42 ms 的 ISP delay 及约 44 ms 的 DQBUF 路径延迟相互吻合，支持“buffer timestamp 是 CIF 帧起始”的解释。

当前没有把传感器 SOF/SOE 脉冲接入逻辑分析仪或示波器，也没有逐行光学曝光实测，因此不能给出 timestamp 到物理曝光开始、中点、结束的确定偏移，更不能声称偏移稳定。应明确采用哪一图像行作为整帧代表时刻，并取得该行曝光中点相对 CIF FS 的传感器时序；之后才可做：

```text
t_image_ref(row) = t_timestamp + δ_CIF_intr + Δ_sensor(row, exposure)
t_ubuntu         = a * t_ego + b
```

其中 `t_timestamp` 当前应视为 CIF FS/SOF 软件时间戳，而不是 EOF。`δ_CIF_intr` 和 `Δ_sensor` 尚未实测；自动曝光变化时 `Δ_sensor` 也不应假定为常数。

## FRAME_SYNC 事件核验

左路媒体拓扑进一步确认：

- `/dev/media1` 是 `rkcif-mipi-lvds1`；
- `/dev/v4l-subdev3` 是 `m00_b_imx334 4-001a`；
- `/dev/v4l-subdev5` 是左路 `rkcif-mipi-lvds1`，其 CIF 子设备代码支持订阅 `V4L2_EVENT_FRAME_SYNC`；
- `/dev/v4l-subdev4` 是左路 `rkisp-isp-subdev`，不是该帧同步事件的源节点。

在设备持续采集时，对 `/dev/v4l-subdev5` 订阅 `FRAME_SYNC` 并等待 8 秒，没有收到事件；订阅过程也没有立即报 `ENOTTY`。结合同版本 Rockchip 6.1 CIF 源码，`FRAME_SYNC` 的用户态入队调用只在部分 LVDS/CCP2 路径中执行，当前 MIPI CSI-2 路径走 `rkcif_sync_sof_to_isp()` 把 SOF 信息送给 ISP，不会向该子设备用户态发送 `FRAME_SYNC`。因此这条路径不能通过 V4L2 事件取得可用 SOF，更不能取得物理 SOE。

## 从物理时刻到 H5 时间字段的延迟分解

这里必须区分两个概念：H5 中保存的相机时间戳代表采集链中的一个事件；文件实际写出时间则是该事件之后几十毫秒甚至更久。当前 `timestamp_ns` 是 CIF FS/SOF 中断处理时调用的 `ktime_get_ns()`，不是 H5 写入时刻。

| 阶段 | 当前设备上的典型量级 | 对 H5 `timestamp_ns` 的影响 |
|---|---:|---|
| 光从场景传播到传感器 | 每米约 3.3 ns | 可忽略 |
| 光电积分/曝光 | 由曝光控制值决定；当前约 33 ms | 不能忽略；不能把曝光时长当作“采样瞬间” |
| 滚动快门逐行时间差 | 当前整帧约 32–33 ms | 不能忽略；不同图像行的采样时刻不同 |
| 传感器输出到 CSI/CIF、硬件识别 SOF | ns 到 µs | 粗对齐可忽略 |
| CPU 中断调度、软件读取单调时钟 | 通常 µs，负载异常时可到 ms | 微秒部分可忽略；目标到亚毫秒时仍需审查异常尾部 |
| CIF FS 软件时间戳写入驱动 buffer | 直接继承 CIF FS 时间 | 这就是当前 H5 `timestamp_ns` 的事件来源 |
| 剩余帧读出、ISP、buffer 排队、DQBUF | 当前中位数约 44 ms | 属于数据到达延迟，不属于 H5 时间戳值 |
| H.264 编码、队列、写盘 | 取决于负载和介质 | 决定文件何时写完，不改变每帧时间戳 |

可把图像参考时刻与 H5 时间戳写成：

```text
t_h5_ts = t_image_ref(row)
        + Δ_shutter_row
        + Δ_sensor_to_cif
        + Δ_irq_clock

t_file_ready = t_h5_ts
             + Δ_readout_isp_queue
             + Δ_encode_write

t_ubuntu = a * t_ego_monotonic + b
```

其中 `Δ_shutter_row` 是针对选定图像行定义的曝光参考时刻到传感器帧事件的有符号偏移，是当前最大的未测量项；它不能简单等同于曝光时长。`Δ_sensor_to_cif + Δ_irq_clock` 通常是纳米到微秒量级，在数十毫秒精度的粗同步中可忽略，但在亚毫秒同步中不能无条件忽略。`t_file_ready` 只描述数据何时可读，不应替代 `t_h5_ts`。

当前左 RGB 为 30 fps、帧周期中位数约 33.333 ms，CIF 报告有效读出约 32 ms，ISP 约 9 ms，所以 timestamp 到 DQBUF 中位数约 44 ms、P95 约 55.7 ms。这是从“帧起始事件”到用户拿到数据的总延迟，不是从真实曝光中点到 H5 时间戳的曝光修正量。跨设备对齐时还要独立求 `a`、`b`；这一项的时钟原点差可以是任意大。

## 30 Hz RGB 与 120 Hz 动捕的时间参考设计

当前约 33 ms 的曝光不能理解为“画面上半幅来自前 15 ms、下半幅来自后 15 ms”。更接近实际情况是：传感器各行依次读出，整幅读出约 32 ms；当前每行又积分约 33 ms。因此每行都在一个接近整帧长的曝光窗口内取平均，而不同行的窗口起点相差最多约 32 ms。高速手部会产生明显拖影，单靠选一个整帧时间戳不能消除这种积分误差。

建议保留以下三个层次，而不是覆盖原始时间戳：

```text
timestamp_cif_fs_ns       H5 原始值，CIF FS/SOF 软件时间
row_readout_ns(y)         = timestamp_cif_fs_ns + row_start(y) * T_line
exposure_mid_ns(y)        ≈ row_readout_ns(y) - exposure_ns / 2
```

其中 `T_line = frame_interval / VTS`。当前 `30 fps`、`VTS=2250`，所以 `T_line≈14.815 µs`。若只给整幅图选择一个时间，建议定义：

```text
t_frame_ref = 图像中心行的曝光中点
```

假设传感器从上向下读出、某行在读出前结束积分且没有额外传感器偏移，则输出中心行相对 CIF FS 的读出时间约 16.1 ms。于是：

```text
t_frame_ref ≈ timestamp_cif_fs_ns + 16.1 ms - exposure_ns / 2
```

按当前约 33.0 ms 曝光，中心行曝光中点约为 `timestamp_cif_fs_ns - 0.4 ms`；如果固定曝光改为 5 ms，则该偏移约为 `+13.6 ms`。这说明偏移会随曝光改变，必须把曝光固定或逐帧记录。上述数值只是未标定的几何初值，不能替代传感器的曝光/读出波形测量。

若要精确处理手部各关键点，应采用逐行时间，而不是给每个点都使用整帧中心时间：

```text
t_keypoint ≈ timestamp_cif_fs_ns
           + sensor_row(y) * T_line
           - exposure_ns / 2
```

左 RGB 配置为 `rotate_180=true`。如果输入算法的是旋转后的 MP4/H5 图像，那么“画面中从上到下”的顺序相对传感器读出顺序可能相反；此时 `sensor_row(y)` 必须按实际图像域重新映射。中心行不受旋转反向影响，但手部位于画面不同高度时，逐行时间会明显不同：图像高度 300 像素对应约 4.44 ms，整幅 2160 像素对应约 32.0 ms。`rotate_180` 是否已在定义关键点坐标之前生效，需要按最终消费的数据域明确记录。

建议采集设置：

1. 关闭自动曝光，固定曝光和模拟增益；否则曝光时长、中心行偏移以及运动拖影都会随场景变化。
2. 在照明允许时缩短曝光。若希望运动拖影小于一个 120 Hz 动捕周期，曝光应优先压到约 8 ms 以下；实际可接受值仍需按手部速度和图像质量检查。
3. 保持 30 Hz 输出；30 Hz 与 120 Hz 的比例为 1:4，不要求把动捕降采样到 30 Hz。
4. 逐帧保存实际曝光、增益、`timestamp_cif_fs_ns`、行时间和图像方向。原始 CIF FS 时间必须保留，派生参考时间另存。

与 120 Hz 动捕对齐时，先用候选 `t_frame_ref` 在相邻动捕样本之间插值，不应取最近的 120 Hz 样本；最近邻本身最多引入约 `±4.17 ms` 误差。高精度方案则计算每个手部关键点所在行的 `t_keypoint`，分别对 3D 点做时间插值，再投影或比较。最终映射为：

```text
t_ubuntu = a * t_image_reference + b
```

`a、b` 及行时序残差应通过运动段标定。可先在若干快速但拖影可用的区间搜索统一时间偏移，再用独立录制段检查残差和长期漂移；不要用待评估的手部算法结果反过来决定同步量。若 33 ms 曝光造成的拖影使关键点已不可靠，则任何时间戳修正都不能恢复实际不存在的瞬时画面，应优先缩短曝光或提供足够照明。

## 当前项目采用的整帧时间简化

2026-10-28 决定：整幅 RGB 使用 H5 的原始 `timestamp_cif_fs_ns` 作为图像参考时间，约 1 ms 以内的中心行曝光中点修正直接忽略：

```text
t_rgb_ref = timestamp_cif_fs_ns
```

该规则不是声称 CIF FS 等于曝光开始或结束，而是把当前 30 Hz、曝光控制 2228 行（约 33.0 ms）条件下，图像中心行曝光中点与 CIF FS 之间约 0.4 ms 的差归入可接受误差。中心行定义不受 `rotate_180` 影响。原始 H5 时间必须保留，另存 `time_policy=center_row_exposure_midpoint__ignored_leq_1ms`、`time_correction_bound_ns=1000000`、实际曝光和图像方向。

使用此简化时必须关闭自动曝光，并至少在录制期间固定 2228 行的曝光控制；帧率仍保持 30 Hz。此规则的适用范围仅限当前约 33 ms 曝光，不能跨越曝光配置复用。若为了减轻手部运动拖影把曝光缩短到 5–8 ms，中心行曝光中点将变成 `timestamp_cif_fs_ns + 约 13.6–14.6 ms`，约 1 ms 简化随即失效。

如果图像用于手部运动精度优先的数据采集，建议关闭自动曝光和自动增益，保持 30 Hz，在灯光或闪光照明允许时使用固定 5–8 ms 曝光。缩短曝光会改善每行 33 ms 的时间积分拖影，但不能消除当前约 32 ms 的滚动快门行间差；时间参考应改用按实际曝光计算的中心行曝光中点或逐行时间。若仍使用固定约 33 ms 曝光，则画面在 1 m/s 的手部速度下也会产生约 33 mm 的运动拖影，时间戳修正不能恢复这部分信息。

与 120 Hz 动捕配对时，先把上述 `t_rgb_ref` 通过 `t_ubuntu = a * t_rgb_ref + b` 映射到动捕时钟，再在相邻有效动捕样本之间插值；位置可插值，朝向用 SLERP。不要把动捕降采样为 30 Hz，也不要用最近邻，后者单是采样离散化就最多引入约 `±4.17 ms` 误差。对每个 RGB 时间保存原始时间、映射时间、所用相邻动捕样本及插值权重，无法形成有效时间区间时标记为无效。
